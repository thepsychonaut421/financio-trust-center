# Coolify application migration impact

- Lifecycle: migrate the existing Trust Center application deployment to Coolify while preserving its existing PostgreSQL/Supabase authentication, application rows, document files, JWT key material when configured and approved content.
- Files/routes: application-only Compose; the existing branch backend/frontend image builds and a no-build recovered-image variant; one ingress for the public portal, Express `/api/*`, Next's exact `/api/revalidate`, and Express `/health`. Separate impact maps describe the additive public branding and private scheduled draft collection; existing publication and document-access behavior stays intact.
- Persistence: no schema or data changes. `public` application tables and the existing Supabase `auth` schema remain authoritative. Document bytes are stored in the backend uploads volume, independently of database rows. This preparation does not create or restore a database, run migrations, seed content or provision credentials.
- Invariants: keep the current service/anon keys and any configured JWT secret together with the restored Auth database; retain document paths and uploads; `DEMO_MODE=false`; admin bootstrap disabled; test email disabled; existing Financio assisted-review and private-document workflows preserved; preserve the actual portal's reviewed content rather than manufacturing certification statements.
- Validation: Compose interpolation/configuration; backend build and tests; frontend build; image build. Before routing: read-only source-vs-target row-count and file-hash comparison, public API contracts, public download, browser administrator login and document access boundaries. Email and write tests require an approved synthetic test and are not implied by read-only readiness.
- Data risk: a new empty volume, incomplete `auth` schema restore, changed JWT/encryption secret or omitted uploads can produce a visually working portal with missing content or invalid accounts. The Compose file requires a named, already restored external uploads volume and explicit Supabase URLs/keys, with no development defaults. Do not invent a JWT secret during migration when the observed deployment did not configure one; integration encryption compatibility must be checked against the observed source.

The recovered-image migration observations are recorded in README.md. New source-release CI and deployment are separate evidence. Dependency addresses and the restored volume name come from the actual Proxmox inventory.
